# HACKTRIBE.bin vs E2_BLUE_202.bin

## Current comparison state

- `HACKTRIBE.bin` is the hacked E2 Sampler firmware; `E2_BLUE_202.bin` is the factory E2 Synth firmware.
- Both use ARM:LE:32:AM1802 and the same broad firmware layout, but code and data regions are not address-identical.
- The source database currently exposes about 3,787 documented/custom-named functions to the cross-binary matcher. The factory database now has 5,710 analyzed functions, including the reconstructed battery/DC boundaries.
- Native Ghidra Version Tracking is still not exposed through the MCP bridge. The bridge's inline-script endpoint is enabled (`GHIDRA_MCP_ALLOW_SCRIPTS=1`) and was used for bounded, repeatable database transactions.

## Important binary differences

- Function addresses are shifted and sometimes reorganized. Matching by identical address is unsafe.
- Some target functions are not split at virtual-function entry points even though target vtables reference those addresses. The battery/DC vtable required reconstruction of three such function boundaries.
- Identical source functions can have different target callees because the two builds use different symbol recovery and surrounding implementation names. Callee-name differences must not be treated as code differences.
- Some source functions have expanded or differently recovered target bodies. For example, the battery event filter and state selector retain the same core state logic but have more target instructions.
- The factory build contains the same battery/DC diagnostic strings: `Battery Check`, `Dc Jack Pull`, and `Power Measurement`.
- Exact normalized transfer: 475 unique source/target matches were found; 472 new target names were applied and 3 existing meaningful target names were preserved. The corresponding signature pass completed for all 475 matches with no reported failures.
- Lower-confidence transfer: 106 unique target-default functions scored from 0.75 to 0.985 in the fuzzy matcher and received source names. No fuzzy transaction failed. Their signatures and class/namespace membership were not copied because the fuzzy score does not prove an exact function-boundary/type match.
- High-confidence fuzzy signatures: the 10 fuzzy matches scoring at least 0.90 were additionally checked against function metrics and received source signatures/types. All 10 transactions completed without failures.
- Remaining candidates below 0.75, ambiguous target collisions, autogenerated source names, and already-meaningful target names remain intentionally untouched. They require separate evidence before promotion.

The destination database was saved after the exact pass, the 106-name fuzzy pass, and the 10-function high-confidence signature pass.

## Transfer policy

1. Promote exact/high-confidence function names first, deduplicating target collisions.
2. Promote signatures, calling conventions, and parameter types only where the target function boundary is verified; the exact pass and the top 10 fuzzy matches meet this bar.
3. Reconstruct class namespaces/vtables when target references support them.
4. Defer comments, labels, globals, and equates until code symbols are complete.
5. Record ambiguous matches and target-only/source-only regions here instead of guessing.

## Transfer tooling

`tools/ghidra/PromoteCrossBinarySymbols.java` performs the repeatable exact matching and promotion. It indexes only named source functions, ignores relocatable address operands, requires a unique source and target fingerprint, and supports bounded `OFFSET`/`LIMIT` transactions. `SIGNATURES` additionally resolves and applies source calling conventions, return types, and parameter types. The separate fuzzy-name pass was applied only to target-default functions and did not copy signatures. Comments were intentionally not copied in this pass.
